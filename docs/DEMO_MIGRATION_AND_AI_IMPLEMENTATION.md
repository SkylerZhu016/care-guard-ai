# 静态 Demo 迁移与 AI 能力落地说明

## 1. 对比分析结论

### 原项目

- Vue 3 前端已有患者、医务、随访和治理四个角色视图，真实状态来自 API。
- Spring Boot v2 问诊已具备版本化目录、事实型症状字段、资料快照、确定性规则和人工终审；v1 新建接口已停用，历史数据只读。
- PostgreSQL/pgvector 保存问诊、规则结果、AI 运行、引用、随访和知识来源；Flyway V1–V9 为已发布迁移。
- Python AI 服务使用异步任务执行审核摘要与 RAG，但旧契约只把 `caseSummary` 保存到业务视图，导致医务端看起来只有一句 AI 文本。

### 静态 Demo

- 统一了顶栏、侧栏、状态标签、预问诊、审核队列、详情分层、弹窗和响应式视觉。
- 患者端强调“选择不适—补充信息—核对提交”；医务端强调“左侧队列—右侧患者事实/规则证据/随访决策”。
- 所有业务数据来自 `ui-demo/src/mock.ts`，提交、审核、分页、告警和知识来源均未连接真实服务。

### 落地取舍

- 保留 Demo 的视觉层级、卡片、标签和审核工作台结构，真实项目现有的四患者功能区、动态安全追问、规则覆盖状态和权限不被 Mock 逻辑覆盖。
- 不删除确定性规则、人工终审、随访激活、治理、历史问诊或安全告警。
- 主诉 AI 是独立辅助阶段。原始文本、患者手选症状、AI 建议标签和患者确认版本分别保存，AI 不直接改写患者选择或规则结果。

## 2. 接口与数据变化

### 新增接口

- `POST /api/v2/visits/{id}/analyze-complaint`：对草稿主诉进行结构化整理。成功和可降级失败均返回稳定对象。
- `PUT /api/v2/visits/{id}/complaint-structure`：保存患者确认、删除或补充后的结果。
- Python 内部接口 `POST /internal/v1/complaint-structure`：只允许内部令牌调用，Pydantic 严格校验输入和输出。

### 扩展接口

- `GET /api/v2/intake-catalog` 升级至 `intake-catalog-2026.07.2`，新增耳鼻喉、骨骼肌肉、泌尿生殖、眼部、睡眠情绪等分类条目。
- `VisitViewV2` 新增 `complaintAnalysis`。
- `TriageViewV2` 新增 `aiSupport`，同时保留 `aiSummary` 兼容旧前端和历史数据。

### V10 数据迁移

- 新表 `visit_complaint_analyses` 保存：原始主诉、运行状态、模型结构、患者确认结构、Provider、模型、提示词版本、耗时和错误码。
- `triage_results.ai_detail` 保存医务端稳定结构化 AI 对象。
- V1–V9 未修改；旧病例没有新对象时仍按原字段读取。

## 3. AI 输出边界

患者主诉结构包含：规范化摘要、提取标签、持续时间、起病、部位、性质、加重/缓解因素、伴随症状、活动影响、风险信号、待追问项和不确定性。

医务端 AI 对象包含：结构化摘要、关键发现、异常信号、待追问问题、重点排查方向、建议补充信息、危险信号、证据综合、不确定性和诊疗思路提示。

所有模型结果均遵循以下约束：

- 不生成最终诊断、处方或剂量建议。
- 不降低确定性规则等级，不为未覆盖症状伪造自动等级。
- 引用必须对应当前有效知识块。
- 超时、HTTP 错误、非法 JSON、Schema 不匹配和安全阻断都会记录失败状态，并转人工复核。

## 4. 配置与启动

默认使用 `AI_PROVIDER=fake` 进行离线开发。真实模型需在未提交的 `.env` 中配置：

```dotenv
AI_PROVIDER=openai-compatible
AI_MODEL=<模型名称>
AI_BASE_URL=<OpenAI兼容接口根地址>
AI_API_KEY=<仅保存在本地环境>
AI_MAX_OUTPUT_TOKENS=1800
```

启动：

```powershell
wsl -d HermesUbuntu -- bash -lc "cd /mnt/d/工程实训/final && docker compose up -d --build"
```

Windows 与 WSL/LibreOffice 之间传递路径时，Windows 使用 `D:\工程实训\final`，WSL 使用 `/mnt/d/工程实训/final`，不要混用 `\` 与 `/`。

## 6. 当前限制

- 自动化测试使用确定性 Fake Provider；真实 DeepSeek/OpenAI 兼容 Provider 需要用户在运行环境注入密钥后做联网质量验收。
- 当前 AI 标签保存在主诉分析记录中，不自动变成确定性规则输入；这是有意的安全隔离。
- 目录扩展条目多数为 `RECORD_ONLY`，新增自动分级规则前仍需医学依据、版本化规则和回归测试。
- RAG 采用“症状主题精确命中优先 + 症状词与分块正文匹配 + 向量相似度排序”的混合召回，同一来源最多取 2 个分块，避免无关主题、长文档中的背景段落或单一来源占满上下文；资料虽可追溯，知识质量仍应按授权、重复度、冲突和临床主题持续治理。
