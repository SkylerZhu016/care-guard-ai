# 患者症状覆盖与随访适配问题报告

> 报告日期：2026-07-22  
> 问题状态：前端与指导文档已按方案 A 处理；服务端目录校验与模板适配仍待后续  
> 建议优先级：高（若项目定位为通用预问诊）；中（若明确限定为胸痛/呼吸困难教学演示）  
> 报告范围：患者端症状录入、确定性分级规则、AI 整理、知识检索、随访模板  
> 项目边界：本项目只处理合成教学病例，不提供诊断、处方或真实医疗建议

## 1. 问题摘要

当前系统并非只能录入“胸痛”和“呼吸困难”。患者端已经可以动态添加、编辑和删除症状，后端也允许接收非固定枚举的症状代码。

真正的问题是：**“允许录入其他症状”与“系统能够安全、完整地处理其他症状”之间存在明显断层。**

- 患者必须手工填写 `HEADACHE`、`FATIGUE` 等英文技术代码，容易误填，且不符合普通患者的使用习惯。
- 后端只校验代码格式，不校验代码是否属于受支持的标准症状字典。
- 确定性规则只明确覆盖胸痛、呼吸困难、晕厥、意识改变和通用严重度阈值。
- 未配置的症状通常得到 `NO_CONFIGURED_RED_FLAG` 和 `ROUTINE`，可能造成“已安全评估”的错误印象。
- Fake AI Provider 的紧急度规则与后端规则同样偏窄，不能补齐症状特异性安全规则。
- 本地测试回退知识仅针对胸痛/呼吸困难、意识改变/晕厥和一个通用常规复核材料。
- 所有审核通过的病例只能创建高血压教学随访计划，激活后固定生成血压记录等任务，与多数主诉不匹配。

因此，若产品定位仍是“胸痛/呼吸困难红旗教学演示”，应在界面和文档中明确限制范围；若要定位成通用基层预问诊平台，则必须扩展症状字典、红旗规则、追问、知识材料和随访模板。

## 2. 用户可见表现

患者页面初始化时预填：

- 主诉：合成胸痛伴呼吸困难
- `CHEST_PAIN` / 胸痛 / 严重度 8
- `DYSPNEA` / 呼吸困难 / 严重度 6

页面提供“＋ 添加症状”，新增后默认为：

- `HEADACHE`
- 头痛
- 严重度 3

患者可以继续修改症状代码、中文名称、起病时间和严重程度。因此，“只能填写胸痛和呼吸困难”并不是当前代码的真实限制。

但是，页面要求患者理解并填写英文代码。例如患者可能输入：

- 正确代码：`HEADACHE`
- 拼写错误但格式合法：`HEADACHEE`
- 自创代码：`VERY_DIZZY`

后两者仍可能通过后端格式校验并入库，但没有对应规则或知识覆盖。

## 3. 源码证据

### 3.1 前端支持动态添加，但采用技术代码输入

文件：`frontend/src/views/PatientView.vue`

- 第 11 行：新增症状默认为 `HEADACHE` / 头痛。
- 第 12 行：初始示例固定为胸痛和呼吸困难。
- 第 15 行：`addSymptom()` 可以添加任意症状行。
- 第 27 行：症状代码使用普通文本输入框，提示为“代码，如 HEADACHE”。
- 第 28 行：提供“＋ 添加症状”按钮。

结论：前端输入能力不是固定两种症状，但交互方式对普通患者不友好，也没有标准化约束。

### 3.2 后端只校验代码格式，不校验业务支持范围

文件：`backend/src/main/java/com/example/medsim/ApiModels.java`

`SymptomInput.code` 只要求匹配：

```text
[A-Z][A-Z0-9_]{1,59}
```

这能阻止小写、空格等非法格式，却不能阻止未知或拼错的症状代码。

### 3.3 确定性规则覆盖范围有限

文件：`backend/src/main/java/com/example/medsim/RuleEngine.java`

当前明确识别：

| 条件 | 结果 | 原因码 |
|---|---|---|
| `ALTERED_CONSCIOUSNESS` | `EMERGENCY` | `ALTERED_CONSCIOUSNESS_RED_FLAG` |
| `CHEST_PAIN` 且伴 `DYSPNEA`、`SYNCOPE` 或最大严重度 ≥ 8 | `EMERGENCY` | `CHEST_PAIN_WITH_RED_FLAG` |
| `DYSPNEA` 或任意症状严重度 ≥ 7 | `URGENT`（至少） | `SEVERE_OR_RESPIRATORY_SYMPTOM` |
| 以上均不满足 | `ROUTINE` | `NO_CONFIGURED_RED_FLAG` |

目前没有看到针对腹痛、头痛神经红旗、消化道出血、严重过敏、高热、抽搐、偏瘫等症状的专门规则。

严重度 ≥ 7 的通用规则能提供部分兜底，但不能替代症状特异性红旗判断。例如某些严重事件并不一定会被患者主观标记为 7 分以上。

### 3.4 AI 可以接收其他症状，但不会自动补齐规则缺口

文件：

- `ai-service/app/workflow.py`
- `ai-service/app/providers.py`
- `ai-service/app/knowledge.py`

工作流会将所有症状代码送入知识检索和 Provider。Fake Provider 也会在摘要中列出输入的症状代码，但其确定性提升逻辑仍主要是：

- 胸痛 + 呼吸困难，或意识改变 → `EMERGENCY`
- 任意症状严重度 ≥ 7 → 至少 `URGENT`
- 其他情况沿用后端规则等级

工作流只阻止 AI 把紧急度降到规则等级以下。它不能保证 AI 为每一种未知症状识别出正确的红旗，也不应由概率模型替代缺失的确定性安全规则。

测试环境的回退知识同样覆盖有限：

- 胸痛伴危险信号
- 意识改变/晕厥
- 无已配置红旗时的通用人工复核

生产模式若使用实际知识服务，覆盖度取决于已入库并激活的指南材料，不能仅凭接口存在就认为所有症状已经受支持。

### 3.5 随访固定为高血压模板

文件：

- `frontend/src/api.ts`
- `backend/src/main/java/com/example/medsim/PlatformService.java`

前端创建计划时默认且实际使用：

```text
HYPERTENSION_TEACHING_V1
```

后端允许的模板集合也只有该模板。激活计划后固定生成：

1. `BP_RECORD`：记录血压数据
2. `SYMPTOM_CHECK`：结构化症状复核
3. `ADHERENCE_CHECK`：教学计划执行情况
4. `CLINICIAN_REVIEW`：第 4 周医务人员复核

这会导致头痛、胸痛、呼吸困难、乏力等不同病例全部进入高血压随访流程。除非病例本身被明确标记为高血压教学病例，否则该行为在业务语义上不成立。

## 4. 影响评估

### 4.1 患者体验

- 技术代码对普通患者不可理解。
- 默认胸痛/呼吸困难会让用户误认为系统只支持该病例。
- 缺少中文搜索、常见症状选择、同义词和分类导航。
- 用户无法知道哪些症状被规则完整支持，哪些只是被保存。

### 4.2 安全与可信度

- 未知代码可能被保存并显示为已完成筛查。
- `NO_CONFIGURED_RED_FLAG` 容易被误读为“没有红旗”，实际含义只是“没有命中当前已配置规则”。
- 其他高风险症状可能被默认分到 `ROUTINE`，再依赖人工审核发现。
- AI 摘要可能提高界面的可信感，却不能证明规则覆盖完整。

### 4.3 随访正确性

- 不同主诉统一套用高血压计划，任务可能与病例无关。
- 随访人员可能收到无业务意义的血压记录任务。
- 数据库中的计划和任务虽然结构合法，但临床教学语义不可靠。

### 4.4 项目定位

项目 README 将系统描述为“基层医疗安全型预问诊与随访平台”，范围看起来比实际规则覆盖更广。当前实现更接近：

> 胸痛/呼吸困难红旗规则 + 受控 AI 摘要 + 人工审核 + 固定高血压随访的教学工程样例。

应避免在未补齐能力前将其描述为可以处理任意症状的通用预问诊系统。

## 5. 建议先做的产品范围决策

在修改代码前，必须从以下两个方向中选择一个。不要一边保持窄规则，一边在界面上暗示通用能力。

### 方案 A：限定为专病教学演示（短期推荐）

- 页面标题、说明和 README 明确写出支持范围。
- 症状只能从已支持字典选择。
- 对不支持的症状显示：“该症状尚未配置自动筛查规则，请转人工教学审核。”
- 不把 `NO_CONFIGURED_RED_FLAG` 显示成“常规/无风险”。
- 高血压随访只允许用于满足高血压教学场景的病例。

优点：修改范围较小，符合当前工程演示基础。  
缺点：不能宣称是通用预问诊平台。

### 方案 B：扩展为通用预问诊（长期方案）

- 建立标准症状字典和同义词映射。
- 扩展症状特异性红旗规则和追问。
- 为规则绑定版本、来源和自动化黄金测试。
- 扩展知识库并验证每类症状的检索命中。
- 增加多种随访模板，并由医务人员明确选择或编辑。
- 对未覆盖症状采用明确的“无法自动分级/必须人工复核”状态。

优点：产品定位和功能一致。  
缺点：需要医疗专业规则设计、知识材料和显著更多测试，不应只改前端。

## 6. 推荐改造范围

以下建议按安全优先级排列，供接手 AI 制定实施计划。

### P0：消除误导和错误默认

1. 将 `NO_CONFIGURED_RED_FLAG` 的语义改为“未配置对应规则，需人工复核”，不能等价展示为“无红旗”。
2. 未知症状代码不得静默进入普通 `ROUTINE` 流程。
3. 随访计划不得无条件使用高血压模板。
4. UI 和 README 明确当前支持范围。

### P1：症状字典与患者端交互

1. 新增后端或共享的症状目录，例如：
   - `code`
   - 中文显示名称
   - 同义词
   - 分类
   - 是否具有已激活规则
   - 规则版本
2. 前端改为中文搜索/选择，代码由系统自动填充且不要求患者编辑。
3. 支持“其他症状”，但必须进入明确的人工复核分支。
4. 初始表单不应自动带入胸痛和呼吸困难；应提供空状态或“加载教学示例”按钮。

### P1：规则与安全状态

1. 为支持的症状定义确定性红旗和必要追问。
2. 将“未命中已配置红旗”和“该症状没有配置规则”区分成不同状态/原因码。
3. 未覆盖症状建议至少返回独立状态，例如 `UNSUPPORTED_REQUIRES_REVIEW`，而不是直接当作 `ROUTINE`。
4. 保留“AI 不得降低规则紧急度”的现有单调性约束。

### P1：随访模板适配

1. 增加模板目录和适用条件。
2. 医务审核完成后，必须明确选择、编辑或决定“不创建随访”。
3. 后端校验模板是否适用于当前病例，不只校验模板名称是否存在。
4. 任务生成逻辑从硬编码迁移到模板配置或模板领域对象。

### P2：知识和 AI

1. 为每个受支持的症状/红旗规则提供可追溯知识材料。
2. 增加检索覆盖测试，确保不同症状命中对应材料，而不是统一返回通用片段。
3. Provider 返回结果继续接受结构化校验、引用白名单和人工审核。
4. AI 只负责整理和补充问题，不得成为缺失确定性规则的替代品。

## 7. 建议数据与接口设计

以下仅作为方向，不要求接手 AI 原样实现。

### 7.1 症状目录示例

```json
{
  "code": "HEADACHE",
  "displayName": "头痛",
  "aliases": ["头疼"],
  "category": "NEUROLOGICAL",
  "ruleCoverage": "ACTIVE",
  "ruleVersion": "headache-red-flags-v1"
}
```

### 7.2 分级结果应区分覆盖状态

```json
{
  "urgency": "ROUTINE",
  "coverage": "SUPPORTED_NO_RED_FLAG_MATCHED",
  "reasonCodes": ["NO_RED_FLAG_MATCHED"]
}
```

或：

```json
{
  "urgency": null,
  "coverage": "UNSUPPORTED_REQUIRES_REVIEW",
  "reasonCodes": ["SYMPTOM_RULE_NOT_CONFIGURED"]
}
```

### 7.3 随访模板选择

计划创建接口不应依赖前端默认值。建议要求医务人员显式提交模板，后端返回适用模板列表并再次校验。

## 8. 验收标准

### 8.1 范围与文案

- [ ] 页面和 README 对支持范围的描述与实际规则一致。
- [ ] 用户能够区分“没有命中红旗”和“系统没有配置该症状规则”。
- [ ] 不再默认把新病例预填成胸痛和呼吸困难，或明确标识为可选教学示例。

### 8.2 症状录入

- [ ] 患者通过中文名称搜索和选择症状，不需要输入英文代码。
- [ ] 标准症状代码由系统生成。
- [ ] 未知/不支持症状不能静默当作已支持症状处理。
- [ ] 至少保留症状名称、起病时间和严重度字段。

### 8.3 规则

- [ ] 支持症状有明确、版本化的确定性规则和来源。
- [ ] 未覆盖症状进入人工复核状态，而不是自动给出普通常规结论。
- [ ] 已有胸痛、呼吸困难、晕厥和意识改变规则保持回归通过。
- [ ] 新增规则具有正常、边界、组合和负向测试。

### 8.4 AI 与知识

- [ ] 其他症状的知识检索能够命中对应材料。
- [ ] AI 不能降低规则紧急度。
- [ ] AI 无法处理、引用无效或知识为空时，病例仍进入安全的人工复核流程。

### 8.5 随访

- [ ] 高血压模板不会被自动用于所有病例。
- [ ] 医务人员可以选择适用模板或不创建计划。
- [ ] 后端拒绝与病例不适配的模板。
- [ ] 不同模板生成的任务与模板定义一致，并有集成测试。

### 8.6 前端可用性与可访问性

- [ ] 症状选择器支持键盘操作、可见焦点和清晰错误提示。
- [ ] 表单标签、按钮和动态新增/删除操作具备可访问名称。
- [ ] 屏幕阅读器能够获知新增症状、验证失败和覆盖状态变化。

## 9. 建议测试用例

至少覆盖以下合成教学病例：

| 病例 | 目的 |
|---|---|
| 胸痛 + 呼吸困难 | 保持现有急症规则回归 |
| 意识改变 | 保持现有急症规则回归 |
| 轻度乏力 | 已支持常规案例或明确未覆盖状态 |
| 轻度头痛 | 验证症状字典、追问和覆盖状态 |
| 头痛 + 神经系统红旗 | 验证新增特异性规则（若选择扩展范围） |

| 拼错代码 `HEADACHEE` | 验证未知代码被拒绝或转为不支持状态 |
| 任意非高血压病例 | 验证不会自动创建高血压随访 |

## 11. 非目标与注意事项

- 本报告不授权把教学系统改成真实临床诊断系统。
- 不应仅通过扩大 AI Prompt 来宣称解决规则覆盖问题。
- 不应把严重度阈值当成所有症状的通用安全规则。
- 不应在缺少专业依据和测试的情况下自行发明医疗规则。
- 本轮只记录问题，没有修改现有功能代码。

## 12. 当前处理状态与完成定义

2026-07-22 已完成的短期安全修正：患者端改为 4 项中文受控目录与空状态，技术代码不可编辑；`NO_CONFIGURED_RED_FLAG` 使用“仍需人工审核”的人类可读解释；医务审核与随访选择分离且默认“不创建”；非高血压教学病例禁用高血压模板；随访任务与知识来源页面完成信息收敛、筛选和分页；README、SRS 与项目开发指导书已同步能力边界。

尚未完成且不能虚假标记为已解决的长期项：服务端仍需提供权威症状目录并拒绝未知代码，分级结果模型仍需机器可读地区分“未命中规则”和“未配置规则”，后端仍需校验模板与病例适配，扩展其他症状时仍需医疗依据、规则、知识和测试共同落地。

该问题只有在以下条件同时满足时才算完成：

1. 产品范围已经明确，并反映在 UI、README 和 SRS 中；
2. 症状输入不再要求患者手工维护技术代码；
3. 规则覆盖状态可被机器和用户明确区分；
4. 未覆盖症状不会静默得到具有误导性的普通结论；
