# 组员 AI 复核建议再审结论（2026-07-23）

## 1. 适用范围

本结论覆盖 `组员复核建议/` 中的三份代码审查报告。报告基于分支 `611` 的较早提交进行静态分析，部分行号、测试数量和运行配置已经落后于当前工作区，因此不直接把报告中的严重级别作为实施依据。

判断顺序为：

1. 回到当前代码确认问题是否仍存在；
2. 判断是否影响当前本地教学/演示部署，而不是假定系统已经对公网生产开放；
3. 判断建议是否会破坏预问诊、草稿恢复、人工审核或 AI 安全边界；
4. 只实施可测试、收益明确且风险可控的修正。

## 2. 本轮已采纳

| 项目 | 再审结论 | 实施结果 |
|---|---|---|
| Python 内部令牌使用普通字符串比较 | 正确，虽为内网接口，仍可低成本加固 | 改为 `hmac.compare_digest` |
| AI JSON 裸对象提取使用贪婪正则 | 正确；简单改成非贪婪又会破坏嵌套 JSON | 改为从每个 `{` 起点使用 `JSONDecoder.raw_decode`，支持嵌套对象、模型说明文字和多个对象 |
| Provider 非超时异常缺少稳定错误码 | 正确 | 将 HTTP 状态、网络连接和响应结构错误分别映射为稳定错误码，不回传响应正文或密钥 |
| 模型 HTTP 超时硬编码 | 正确 | 新增 `AI_REQUEST_TIMEOUT_SECONDS`，默认保持 20 秒 |
| 主诉确认接口未再次校验目录代码 | 正确 | 确认标签必须仍存在于当前服务端目录；非自定义标签的显示名和分类由目录重新补齐 |
| 前端 `fetch` 没有超时 | 正确 | 默认 30 秒主动中止；知识重建允许 120 秒；统一返回 `REQUEST_TIMEOUT` 或 `NETWORK_ERROR` |
| 同一草稿重试时重新生成提交键 | 部分正确；不会凭空创建新 visit，但会破坏“同一次提交返回同一结果”的语义 | 提交键改为由 visit ID 确定生成，同一草稿重复调用保持一致 |
| 未知路由显示空白页 | 正确 | 增加 404 兜底并重定向到登录入口 |

## 4. 确认存在但本轮暂不局部修补

### 4.1 提交事务内等待 AI

`IntakeV2Service.submit()` 目前确实在数据库事务中等待异步 AI 作业完成。简单地把 HTTP 调用移出事务会引入新的失败状态：进程在两段事务之间退出时，visit 可能永久停在 `PROCESSING`。正确修复需要一起设计：

- 提交短事务；
- 持久化 AI 作业关联；
- worker 回调或后台消费最终结果；
- `PROCESSING` 超时回收；
- 重复回调幂等；
- 前端轮询审核状态。

因此不采用只挪一行调用的降级方案，后续应作为独立重构实施并补充故障恢复测试。

### 4.2 浏览器草稿中的医疗文本

`localStorage` 长期保存主诉确实不适合真实患者环境，但当前需求同时要求自动保存、退出和恢复。后续应迁移为服务端草稿自动保存、设置保存期限，并在共享设备提供明确清除入口；不采用固定密钥前端加密。

### 4.3 审计请求关联

审计日志目前使用独立随机 request ID，不能串联一次 HTTP 请求内的多条记录。应统一增加请求过滤器、MDC 和 `X-Request-Id` 传递后再改，避免只在某一个 Service 中读取请求对象。

### 4.4 AI 作业恢复与连接复用

worker 崩溃后 `RUNNING` 状态的回收、Celery time limit、Redis/HTTP 客户端生命周期都有优化价值，但需要结合任务重试是否会产生重复模型费用和重复写入一起设计，不能只打开自动重试。
